BattleFrameBattleControl 行为逻辑剖析

以"索敌 → 接近 → 攻击 → 切换目标 → 受击 / 避障"五个场景为线索，剖析 ABattleFrameBattleControl::Tick 如何用纯 ECS 流水线驱动数万实体的战斗 AI（不依赖 StateTree / BehaviorTree）。

核心结论：BattleFrame 完全不使用 UE 的 AI 框架。它用 「Trait 标签 + 枚举子状态 + 顺序 System 流水线」 自己实现了一套群体 AI 决策机制。AI 行为是各独立 System 顺序执行后涌现出来的， 而非任何单点的决策树输出。
① 架构图 ② 架构总览 ③ 三层状态机 ④ Tick 流水线 ⑤ 五个场景剖析 ⑥ AgentTrace 深度剖析 ⑦ 一生时间线 ⑧ 设计取舍

关键认知：BattleControl 这个 Actor 不持有任何实体。所有 agent 都活在 Apparatus Mechanism 里。 BattleControl 只是每帧拉一遍 Mechanism，用 Filter 挑出符合条件的子集，并发地改它们的 trait。 跨 System 通信也不靠函数调用，全靠"上一个 System 写 trait，下一个 System 读 trait"。

② 架构总览

ABattleFrameBattleControl 是一个普通的 UE Actor，但它的 Tick() 函数包揽了整个战斗框架的全部逻辑 ——从巡逻、索敌、追击、攻击、受击、伤害结算、debuff、死亡、动画状态机、渲染数据回传……都在同一个 Tick 里顺序跑完。

核心调用范式

auto Chain = Mechanism->EnchainSolid(AgentXxxFilter);  // 按 Trait 过滤实体
Chain->OperateConcurrently(
    [&](FSolidSubjectHandle Subject,
        FLocated& Located,
        FMove&    Move,
        ...
    ) {
        // 多线程：每个匹配的实体执行一次
        // 直接读写 trait，输出新状态 / 加 trait / 删 trait
    },
    ThreadsCount, BatchSize);

完整 Filter 列表见 BattleFrameBattleControl.h:148-180，共 30+ 个 Filter，每个对应一个 System 子阶段。

③ 三层叠加的"状态机"

项目没有任何一个 StateMachine 类。"状态"由三种机制叠加表达：

层级机制粒度典型用途
1. Trait 标签 空结构体 trait 当 tag 用 粗（活/死/睡/打/挨打） 过滤器分发：决定谁进入哪个 System

3. Flagmark 位 EFlagmarkBit::A~M 瞬时（事件触发位） 动画优先级、一次性触发

④ Tick 流水线全貌

下面是 ABattleFrameBattleControl::Tick 每帧的固定执行顺序（精简版）：

Tick(DeltaTime): ├─ Statistics // 统计存活数 ├─ AgentAppearMain // 处理 FAppearing：延时出场、播 Appear 动画 ├─ AgentSleep // 处理 FSleeping：被唤醒条件 ├─ AgentPatrol // 巡逻路径生成、等待计时 ├─ SpeedLimitOverride // 速度上限覆盖 │ ├─ ★ AgentMove // 主移动循环：导航 + RVO2 避障 + 重力 + 转向 ├─ Update NeighborGrid // 重建空间哈希，供下一步查询 │ ├─ ★ AgentTrace // 索敌：扇形 trace by Traits，写 Tracing.TraceResult ├─ ★ AgentAttackTrigger // 距离/角度通过 → SetTraitDeferred(FAttacking) ├─ ★ AgentAttacking // 推进 EAttackState 子状态机 │ ├─ SpawnProjectile // 攻击产生的子弹 ├─ Projectile Move and Dmg // 子弹飞行 + 伤害结算 │ ├─ ★ SubjectBeingHit // 受击：扣血 + 击退 + 加 FBeingHit ├─ AgentSlowed // 减速 debuff 累积 ├─ AgentTemporalDamaging // 持续伤害 ├─ AgentDeath // 死亡：FDying 实体的清理 │ ├─ SpawnActors / Fx / Sound // 攻击/受击/死亡的特效音效 ├─ EventInterface // 把队列里的事件派发给蓝图 (OnAttack/OnHit/OnDeath) ├─ Agent Anim State Machine // 动画优先级仲裁（hit 打断 attack 等） └─ AgentRender / SendDataToNiagara // 写到 Niagara 数据通道
关键洞察：每个 System 都只做"看 trait → 算 → 改 trait"，没有任何 "我现在要决策做什么"的中央调度。所谓 AI 行为，是这条流水线跑完后涌现出来的。

⑤ 五个场景的实现剖析

场景 ① 索敌：找到敌人在哪里

实现位置：AgentTrace System，BattleFrameBattleControl.cpp:1475-2006 （具体实现见第 ⑥ 节"AgentTrace 深度剖析"）

触发时机：每帧扫描所有带 FTrace + FTracing + FMove + FLocated trait 的实体， 根据 Moving.MoveState 决定是否要重新索敌（不同状态有不同冷却）。

两种索敌模式（ETraceMode）：

  • TargetIsPlayer_0：粗暴模式，目标永远是玩家 0（适合塔防杂兵）
  • SectorTraceByTraits：通过 NeighborGrid 做扇形空间查询，按 trait 过滤候选

结果写入：Tracing.TraceResult（一个 FSubjectHandle）。 这就是后续所有"目标依赖"逻辑的唯一信源。

场景 ② Move to：移动到可攻击范围

实现位置：AgentMove System，BattleFrameBattleControl.cpp:448-1452 （约 1000 行，全项目最复杂的 System）

核心：Move 状态机的 4 选 1 优先级（cpp:534-635）：

if (bIsSleeping)             Moving.MoveState = Sleep_Sleeping;
else if (bIsPatrolling)      Moving.MoveState = Patrol_(Patrolling|Waiting);
else if (bIsChasing)         Moving.MoveState = Chase_(Chasing|Reached);
else                        Moving.MoveState = Approach_(Approaching|Arrived);

"接近敌人"的本质（cpp:701-755）：当 Tracing.TraceResult 有效时

if (bHasValidTraceResult && bIsTraceResultHasLocated) {
    Moving.Goal = Tracing.TraceResult.GetTrait<FLocated>().Location;
    Moving.bHasGoal = true;
}

导航三层回落（节省群体性能的关键）：

有索敌目标？
├ 是 → 目标绑了 FlowField (FBindFlowField)?
│       ├ 是，自己在该流场内 → 用目标流场（O(1) 查询，群体最便宜）
│       └ 否 → A* / 直冲
└ 否 → 自己在 Base FlowField 内？
        ├ 是 → 用 Base 流场
        └ 否 → A* / 直冲

速度叠乘（cpp:758-807）：基础速度先按状态乘倍率，再被减速/转向角/到目标距离层层削减； 最后用 V²/2A 物理刹车公式判定是否该减速停止。

RVO2 避障（cpp:894-1101）：

  1. NeighborGrid->GetNeighborCells 查空间网格
  2. 过滤距离、去重、排除 FDying、按 AvoGroup0~9 过滤
  3. MaxHeap 只保留最近 MaxNeighbors 个（避免 O(n²) 爆炸）
  4. ComputeAvoidingVelocity：RVO2 算法本体，输出新速度
  5. 对障碍物（Box / Sphere）再跑一遍
  6. VInterpConstantTo 平滑过渡（避免抽搐）

场景 ③ Attack：发起攻击

这个场景被拆成两个独立 System：

3A) AgentAttackTrigger（cpp:2011-2078）

判断"能不能开打"：

if (!Subject.HasTrait<FAttacking>()) {                // 还没在打
    bool bIsTargetValid = Tracing.TraceResult.IsValid()
        && !Tracing.TraceResult.HasTrait<FDying>()
        && Tracing.TraceResult.GetTrait<FHealth>().Current > 0;

    if (bIsTargetValid) {
        float DistSquared = FVector::DistSquared(SelfLoc, TargetLoc);
        float CombinedRadius = Attack.Range + SelfRadius + OtherRadius;

        if (DistSquared <= FMath::Square(CombinedRadius)) {
            Subject.SetTraitDeferred(FAttacking());   // ★ 加上 FAttacking 标签
            // 发 Aiming 事件给蓝图
        }
    }
}

3B) AgentAttacking（cpp:2083+）

已经在打的实体，推进 EAttackState 子状态机：

Aim_FirstExec  →  Aim            // 瞄准期，强制转向目标
              ↓
PreCast_FirstExec  →  PreCast    // 前摇：播攻击动画，不可被打断
              ↓
PostCast                          // 后摇：到 TimeOfHit 时刻应用伤害
              ↓
Cooling                           // 冷却
              ↓
Completed       →  RemoveTrait<FAttacking>()

伤害应用时机：到达 PostCast 的 TimeOfHit 时刻，调用 ApplyPointDamageAndDebuff / ApplyRadialDamageAndDebuff / 生成 Projectile。

为什么拆两个 System？ Trigger 和 Attacking 用不同的 Filter：
AgentAttackFilter 不要 FAttacking，AgentAttackingFilter 必须有 FAttacking。
这样能让 ECS 直接按 archetype 分桶，并行度更高，并避免一帧内对同一实体反复检查。

场景 ④ 敌人被消灭后，寻找下一个目标

分布在多个 System 协作完成，没有任何中央调度。链路如下：

帧 N：SubjectBeingHit System 给目标扣血，如果 Health <= 0 → SetTrait(FDying())
帧 N：AgentAttacking System 在 Aim 阶段检查目标 → 发现 TraceResult.HasTrait<FDying>() → 立刻 RemoveTraitDeferred<FAttacking> + Tracing.TimeLeft = 0（cpp:2112-2118）
帧 N+1：AgentTrace System 看到 TimeLeft == 0 → 重新做扇形索敌 → 找到新目标 → 写入 TraceResult
帧 N+1：AgentMove 的状态机分支命中 bIsChasing → Moving.Goal 改成新目标位置
帧 N+1+：开始接近新目标，循环重启

关键点：目标失效检测在多处独立完成，而非依赖死亡事件回调：

  • AgentTrace 内：返回结果时排除 FDying
  • AgentAttackTrigger 内：触发前再次确认目标 alive
  • AgentAttacking::Aim 内：每帧检查 TraceResult 是否仍合法
  • AgentMove::Chase 分支：bIsChasing = Chase.bEnable && bHasValidTraceResult

这种"各处独立检查，不依赖事件"的写法在 ECS 里是常态——因为系统是数据驱动的、并发的、无序通信的。

场景 ⑤ 自己受到攻击时的反应

项目没有"主动逃跑"行为，但提供了三种"被动反应"：

5A) 受击中断（SubjectBeingHit，cpp:3005-3247）

  • 给受击实体加 FBeingHit trait
  • 触发 HitAnimFlag → 下一帧 Anim State Machine 切到 EAnimState::BeingHit
  • 打断当前攻击：在 Anim State Machine 里（cpp:4425-4445）： 
    if (bIsHitAnim) {
    bIsHitAnim = Subject.HasTrait<FAttacking>()
        ? Attacking.State != PreCast    // 前摇不能被打断
        : bIsHitAnim;                   // 但后摇可以取消

    if (bIsHitAnim)
        Subject.SetFlag(AttackAnimFlag, false);  // hit 优先级 > attack
}
  • 击退（launch）：通过 Moving.LaunchVelSum 注入冲量，AgentMove 下一帧累加到速度上

5B) 群体避障（AgentMove 内嵌 RVO2）

每帧每个实体都会跟邻居做 RVO 互让。这不是"看到危险逃跑"，而是群体动力学—— 防止数千实体挤成一团。攻击中速度自动 ×0.25（cpp:901），让攻击者"扎根"，逃跑者绕过他们。

5C) 减速 / 持续伤害 debuff

FDebuff trait 携带配置，FSlowing / FTemporalDamaging 是状态承载。 AgentSlowed 和 AgentTemporalDamaging System 每帧把减速效果叠乘到 Slowing.CombinedSlowMult， AgentMove 在算 DesiredSpeedMultiplier 时自动应用。

没实现的"主动躲避"： 如果想要"血量低于 20% 时逃跑"，需要自己添加：
① 新 trait FFlee（配置） + FFleeing（标签）
② 新 System AgentFlee，插在 AgentMove 之前
③ 满足条件时 SetTrait(FFleeing) 并改写 Moving.Goal（反向远离）
④ 状态机里加 EMoveState::Flee_Fleeing

⑥ AgentTrace 深度剖析

AgentTrace 是整个 AI 决策环里"感知"的部分 —— 它不直接下决定下一步去哪里、要不要打， 而是输出一个唯一信源：Tracing.TraceResult。其它所有 System（AgentMove 的 Chase 分支、AgentAttackTrigger 的触发判断、AgentAttacking 的目标失效检测）都读这一个值。

位置与契约

// Filter 定义（cpp:4845 附近）
AgentTraceFilter = FFilter::Make<FAgent, FLocated, FTrace, FTracing,
                              FMove, FMoving, FActivated>();

// 主调用（cpp:1503）
auto Chain = Mechanism->EnchainSolid(AgentTraceFilter);
Chain->Retain();

整体架构：两阶段并发

这是 AgentTrace 跟其它 System 最大的不同 —— 它拆成了两个并发遍历：

// Phase A: 决定"该不该 trace" → 收集候选列表 (cpp:1511-1616)
Chain->OperateConcurrently([&](Subject, Located, Trace, Tracing, Moving) {
    // 1. 冷却倒计时 / 状态判断 → 决定 bShouldTrace
    // 2. 命中的塞进 per-thread 数组 ValidSubjectsArray[ThreadId%N]
    // 3. 这一阶段不做任何空间查询，便宜
}, ThreadsCount, BatchSize);

// 收集所有线程的结果，去重 (cpp:1618-1623)
TArray<FSolidSubjectHandle> ValidSubjects;
for (auto& a : ValidSubjectsArray) ValidSubjects.Append(a.Subjects);

// Phase B: 对候选名单做真正的扇形查询 (cpp:1626+)
ParallelFor(ValidSubjects.Num(), [&](int32 i) {
    // 1. 拿到所有相关 trait 引用
    // 2. 按 MoveState 选合适参数（视野半径/角度/高度）
    // 3. 执行 SectorTraceForSubjects 空间查询
    // 4. 写 Tracing.TraceResult
});

Chain->Release();
Mechanism->ApplyDeferreds();
为什么要拆两阶段？
Phase A 工作量很小（就是看几个 bool 和倒计时），适合 chain 遍历——所有实体都过一遍，便宜。
Phase B 包含 NeighborGrid->SectorTraceForSubjects 这种重操作，每个实体几十~几百次距离/角度检查。
分开后：① Phase A 几乎零开销筛掉绝大多数实体（冷却中 / 不能 trace / 处于 attacking 等）； ② Phase B 只对真正需要的实体跑，ParallelFor 切片更均匀（不会出现大量"啥都没干就退出"的薄任务）。

Phase A 细节：按 MoveState 切冷却

if (Trace.bEnable && !bHasAttacking) {       // ★ 攻击中绝不索敌
    if (Tracing.TimeLeft <= 0) {              // 冷却到了
        switch (Moving.MoveState) {
            case Sleep_Sleeping:
                bShouldTrace = Sleep.bCanTrace;
                Tracing.TimeLeft = Trace.SectorTrace.Sleep.bEnable
                    ? Trace.SectorTrace.Sleep.CoolDown
                    : Trace.SectorTrace.Common.CoolDown;     // fallback
                break;
            case Patrol_Patrolling: /* 用 Patrol.CoolDown */
            case Patrol_Waiting:    /* 同上 */
            case Chase_Chasing:     /* 用 Chase.CoolDown */
            case Chase_Reached:     /* 同上 */
            case Approach_*:        /* 用 Common.CoolDown */
        }
    } else {
        Tracing.TimeLeft -= SafeDeltaTime;     // 普通倒计时
    }
}

为什么按 MoveState 分桶冷却？

  • 休眠中：可以慢点扫（节能），但能配置"睡觉时是否还能被视野唤醒"
  • 巡逻中：中等频率，需要发现新敌人
  • 追击中：高频率，要确认目标是否还在视野/还活着
  • Approach（一般移动）：用 Common 默认值

每个 FSectorTraceParamsSpecific 都有 bEnable 开关，关闭时退回 Common。设计师能在编辑器里为同一个怪在不同状态下配不同视野（比如 sleeping 视野很小，chasing 视野大）。

Phase A 的并发收集技巧

// per-thread ValidSubjectsArray，避免争抢全局数组
uint32 ThreadId = FPlatformTLS::GetCurrentThreadId();
uint32 Index = ThreadId % ThreadsCount;

if (LIKELY(ValidSubjectsArray.IsValidIndex(Index))) {
    ValidSubjectsArray[Index].Lock();                      // 子数组独立锁
    ValidSubjectsArray[Index].Subjects.Add(Subject);
    ValidSubjectsArray[Index].Unlock();
}

作者明确写了注释："this may not evenly distribute, but well enough"。 线程哈希分桶简单粗暴，可能有点不均匀，但远比一把全局锁高效。

Phase B 细节：两种 Trace 模式

模式 1：ETraceMode::TargetIsPlayer_0

玩家在哪儿？通过 UGameplayStatics::GetPlayerPawn(World, 0)→FindComponentByClass<USubjectiveActorComponent> 拿到玩家的 Subject（玩家也是个 ECS 实体）。

在 Phase B 前一次性确认玩家有效性（cpp:1477-1500）：

bPlayerIsValid = PlayerHandle.IsValid()
              && !PlayerHandle.HasTrait<FDying>()
              && PlayerHandle.HasTrait<FLocated>()
              && PlayerHandle.HasTrait<FHealth>()
              && PlayerHandle.GetTrait<FHealth>().Current > 0;

每个实体的判定走四步漏斗，从便宜到贵：

① 高度差 : |Player.Z - Self.Z| <= FinalHeight │ （一次减法） ▼ ② 距离平方 : Dist²(Self, Player) <= (Range + Radius)² │ （不开方，纯乘法） ▼ ③ 扇形角度 : acos(dot(Directed.Direction, ToPlayerDir)) <= Angle/2 │ （一次点积 + 一次 acos） ▼ ④ 可见性检查 : SphereTraceSingleForObjects(Self, PlayerSurface, ObstacleType) （这是最贵的，所以放最后；可通过 bCheckObstacle 关掉） ▼ Tracing.TraceResult = PlayerHandle ✓

这是典型的早期退出优化——前三步不通过直接 break，SphereTrace 这种引擎调用只在最后一步触发，并且只对单一目标做一次（玩家就一个），不需要遍历邻居网格。

模式 2：ETraceMode::SectorTraceByTraits

用于"找一群可能的目标里最近的那个"。核心是 NeighborGrid->SectorTraceForSubjects：

Tracing.NeighborGrid->SectorTraceForSubjects(
    1,                          // 只要 1 个结果
    Located.Location,           // 检测原点
    FinalRange,                 // 检测半径
    FinalHeight,                // 检测高度（柱体高度）
    TraceDirection,             // 扇形朝向（= Directed.Direction.GetSafeNormal2D()）
    FinalAngle,                 // 扇形角度
    bFinalCheckVisibility,      // 是否做 LOS 检查
    Located.Location, 0,         // CheckOrigin (障碍物穿透起点)
    ESortMode::NearToFar,     // 排序：从近到远
    Located.Location,           // SortOrigin
    IgnoreList,                 // 忽略列表（含自己）
    Trace.Filter,               // ★ Trait 过滤（包含/排除标签）
    DebugConfig,
    Hit, Results
);

if (Hit && Results[0].Subject.IsValid()) {
    Tracing.TraceResult = Results[0].Subject;     // 只取最近的
}

FBFFilter Trace.Filter 的设计：可以分别配置 "IncludeTraits"（必须有这些 trait）和 "ExcludeTraits"（不能有这些 trait），以及 ObstacleObjectType（用于 LOS）。例如配一个怪只攻击玩家阵营且会飞的目标，就 Include FAgent + FFlyable + Team0，Exclude FDying。

跨状态的副作用：丢失目标 → 回到巡逻

// Go back to patrol state when no target (cpp:1991-1999)
const bool bShouldPatrol = !bHasValidTraceResult
    && !Subject.HasTrait<FPatrolling>()
    && Patrol.OnLostTarget == EPatrolRecoverMode::Patrol;

if (bShouldPatrol) {
    FPatrolling NewPatrolling;
    ResetPatrol(Patrol, NewPatrolling, Located);
    Subject.SetTraitDeferred(NewPatrolling);  // 加 FPatrolling 标签
}

这是 AgentTrace 唯一一处会"主动改变其它 trait"的地方 —— 追击目标丢失（trace 失败）后，根据 FPatrol.OnLostTarget 设置决定是否回到巡逻状态。 下一帧 AgentMove 看到 FPatrolling，状态机分支会自动切到 Patrol_*，重启巡逻循环。

事件队列：通知蓝图层

// Trace 开始事件
if (bShouldTrace && bHasIsSubjective) {     // 只有 Actor 桥接的实体才发
    FTraceData TraceData;
    TraceData.SelfSubject = FSubjectHandle(Subject);
    TraceData.State = ETraceEventState::Begin;
    OnTraceQueue.Enqueue(TraceData);              // MPSC 无锁队列
}

// Trace 结束事件
TraceData.State = bHasValidTraceResult
    ? ETraceEventState::End_Reason_Succeed
    : ETraceEventState::End_Reason_Fail;
OnTraceQueue.Enqueue(TraceData);

这些事件由后面的 EventInterface System（cpp:4149+）统一出队，在主线程派发给挂着 UBFSubjectiveAgentComponent 的 Actor 的蓝图事件接口（OnTraceStart / OnTraceSucceed / OnTraceFail），让用户写蓝图能响应。

关键设计点小结

设计原因
两阶段（gather → ParallelFor） Phase A 极轻量，过滤掉 90% 实体；Phase B 重操作只对剩下的跑，并行更均匀
per-thread ValidSubjectsArray + 子数组锁 避免全局锁竞争，简单哈希分桶
四步漏斗 (高度→距离²→角度→LOS) 按计算成本递增排序，前三步全是数学运算，最后才碰引擎 API
距离判定全程用距离平方 避免开方，距离 < R 等价于 dist² < R²
按 MoveState 切冷却 + 视野参数 设计师可分状态调（睡觉视野小、追击视野大），数据驱动
!bHasAttacking 直接跳过 攻击中不应该切目标，否则会"瞄一半改瞄别人"破坏体验
失败时按 OnLostTarget 切回巡逻 跨 System 用 trait 沟通：本 System 只负责设 FPatrolling，AgentMove 自动接管
事件入 MPSC 队列，主线程统一出队 蓝图回调不是线程安全的，并发 lambda 内禁止直接 call

⑦ 一个实体"攻击玩家"的完整时间线

把五个场景串起来，看一个杂兵从巡逻到攻击到换目标的完整生命周期：

帧 1（巡逻中）
FPatrolling trait 在身上，MoveState = Patrol_Patrolling。
AgentPatrol 生成新 Moving.Goal。
AgentMove 按 Goal 计算速度，RVO 避开同伴。
帧 K（发现敌人）
AgentTrace Phase A：Tracing.TimeLeft 归零 → 加入 ValidSubjects。
AgentTrace Phase B：扇形 trace → 命中玩家 → 写 Tracing.TraceResult。
帧 K+1（开始追击）
AgentMove：bIsChasing == true → MoveState = Chase_Chasing。
Moving.Goal = TraceResult.Location，开始接近。
帧 L（进入攻击范围）
AgentAttackTrigger：距离 < Attack.Range → SetTraitDeferred(FAttacking())，发 EAttackEventState::Aiming 事件。
帧 L+1 ~ L+N（攻击中）
AgentAttacking 推进 EAttackState： Aim_FirstExec → Aim → PreCast（点亮 AttackAnimFlag，播攻击动画）→ PostCast（到 TimeOfHit 时应用伤害）→ Cooling → Completed → RemoveTrait<FAttacking>()。
帧 M（攻击间被自己受击中断）
被其他怪打中 → SubjectBeingHit 给 FBeingHit。
若当前不在 PreCast → Anim State Machine 切到 BeingHit，AttackAnimFlag 清除。
Moving.LaunchVelSum 累加击退冲量，下帧 AgentMove 应用。
帧 P（目标死亡）
SubjectBeingHit 检测玩家 Health <= 0，给玩家 FDying。
AgentAttacking::Aim 下一帧检查 → 发现 TraceResult.HasTrait<FDying>() → 立即 RemoveTrait<FAttacking> + Tracing.TimeLeft = 0。
帧 P+1（自动换目标）
AgentTrace 立即重新扫描 → 找到下一个目标 → 写入 TraceResult。
AgentMove 下一帧 bIsChasing = true → MoveState 回到 Chase_Chasing。
帧 Z（自己阵亡）
SubjectBeingHit 检测自身 Health <= 0 → SetTrait(FDying)。
AgentDeath 处理动画、特效、延时 Despawn。
其他实体的 trace / attack 都因 HasTrait<FDying> 检查自动忽略它。

⑧ 关键设计取舍

设计决策原因
不用 StateTree / BehaviorTree 它们是 per-Actor 的 UObject 树，几千实体性能崩溃。ECS 流水线天然并行。
Trait 标签 + enum 子状态 + Flagmark 三层叠加 粗粒度过滤靠标签（archetype 分桶），细粒度推进靠 enum（数据），瞬时事件靠 Flagmark（位运算最便宜）。
Attack 拆 Trigger + Attacking 两个 System 不同 Filter → 不同 archetype 桶 → 并行度更高。同时避免一帧内重复判定。
AgentTrace 拆 gather + ParallelFor 两阶段 Phase A 极轻量先过滤大多数；Phase B 的重查询只对候选跑，切片更均匀。
目标失效的"分布式检查" 不依赖事件回调。每个 System 在用到 TraceResult 前自己确认 alive，ECS 系统天然解耦。
FlowField > A* > 直冲 三层导航回落 FlowField 烘焙一次群体共享 O(1)；A* 单人精度；直冲兜底。按场景成本递增。
RVO2 + NeighborGrid + MaxHeap 截断 RVO2 数学严谨，但 O(n²)；网格查询限制邻居范围，堆维护只保留最近 N 个。
大量使用 SetTraitDeferred / RemoveTraitDeferred 并发 lambda 内直接改 archetype 会导致迭代器失效；deferred 操作在帧末统一提交。
距离判定全程用距离平方 避免开方，距离 < R 等价于 dist² < R²。
速度积分用 VInterpConstantTo 而非直接赋值 让群体有"惯性感"，避免大量实体同帧瞬变方向造成的视觉抽搐。
所有事件入队（OnAttackQueue / OnHitQueue / OnDeathQueue / OnTraceQueue），EventInterface 统一派发 蓝图回调不能在并发 lambda 里调（不线程安全），用 MPSC queue 解耦。
一句话总结： BattleFrameBattleControl::Tick 是一条固定顺序、纯数据驱动、全程并发的 ECS 流水线。 你描述的"索敌→Move→Attack→换目标→受击"五个行为，在项目里被解耦成 AgentTrace / AgentMove / AgentAttackTrigger / AgentAttacking / SubjectBeingHit 五个独立 System， 它们之间不直接调用，只通过 Tracing.TraceResult、Moving.Goal、 FAttacking、FBeingHit、FDying 这些共享 trait 通信。 这种范式牺牲了 StateTree 的可视化与可读性，换来 25,000 agent / 60fps 的群体战斗性能。
